Jev (TypeSafe System One) is text-only — a synthetic red image sent in 3 formats got "none" each time and no extra input tokens (tested 2026-10-10). So photo naming = two steps: Claude looks at the photo and writes a neutral one-line description (part, side, damage; no part name), then Jev picks from the fixed item-name list ([[car-part-item-names]] master list) with a confidence; below gate -> human review. Only text goes to the API.

Trial on CDD5894 photos 1001-1027 (2026-10-10, 24 photos): user confirmed ALL 24 correct, including Headlamp RH for 1015/1016/1019/1022/1023 where I doubted Jev (0.61-0.66 conf on 1015/1016 was still right) — so the 0.60 gate was not too loose on this set.

**Why:** earlier Claude (Opus 4.5) kept mis-seeing/mis-naming photos; user wants a gated, fixed-vocabulary step.
**How to apply:** send max ~4 questions per request and pre-filter candidates by zone (front/rear/side/identification) — the full ~300-name list returns `max_tokens_exceeded`. Trial script: scratchpad `photo_trial.py` (not in repo). User never names photos manually.

Second batch CDD5894 1028-1082 (44 photos), compared with the Merimen photo captions (Merimen photo order = Desktop file order, 1:1 after ID shots): only ~10 exact + 6 near-name matches. User overrides (Merimen was wrong): 1039 = Front Panel; 1040-1042 = Front Bumper Reinforcement. Failure causes: (a) names missing from the candidate list (Front Number Plate, Front Panel Assembly, Front Bumper Bracket, Radiator Air Deflector RH); (b) my descriptions wrong on internal parts and LH/RH; (c) the adjuster's habit of naming a whole photo sequence after one part. Merimen captions are NOT fully reliable ground truth.
Idea to try next: use the case's own estimate part rows as the candidate list, group consecutive photos, and later a kNN over past Merimen photo+caption pairs.
