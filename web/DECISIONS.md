# web/ decisions

- Stack as in plan.md §3: Next.js 15 App Router, Drizzle on Neon (neon-http), Better Auth (email+password, verification, reset), Resend, Vercel Blob.
- Blobs are uploaded with `access: "private"` under `<orgId>/…` (files hold NRIC/addresses). The upload route rejects paths outside the caller's org.
- Org is created at sign-up by a Better Auth `user.create.after` hook (neon-http has no transactions; two inserts).
- Password minimum 8 chars (`MIN_PASSWORD` in `lib/i18n.ts`); email verification required before login.
- `src/db/index.ts` is lazy so `next build` works without secrets; a localhost DATABASE_URL uses node-postgres (tests only).
- Migrations: `drizzle/*.sql` (generated by drizzle-kit), applied by `npm run db:migrate` (tracks `_migrations`).
- Stage-2 tables (merimen_connections, jobs, usage, credits) are created now so the schema is stable; nothing uses them yet.
- Privacy/terms pages are placeholders; owner supplies legal text.
- Brand name: **Autopilotclaim** (owner, 2026-11-14; domain autopilotclaim.com bought, DNS on Vercel). Mail is sent from `EMAIL_FROM="Autopilotclaim <noreply@autopilotclaim.com>"` once the Resend domain is verified (until then use the Resend test sender). The test sender only delivers to the Resend account owner's own email address, so only that address can complete sign-up in production for now.
- No domain will be bought for now (owner, 2026-11-14): deploy on the default *.vercel.app URL.

## Photo naming desk (plan #9, 2026-11-15)
- Page `/cases/<id>/photos`. Everything the old shared naming page did (names, copy/paste, order, extra parts, undo, shortcuts, done) now lives in the app, in the Night Bay style.
- Names come from Claude (`claude-sonnet-5-5`; another model only through env `CLAUDE_MODEL_PHOTOS`). Photos go to Anthropic only. **TypeSafe ("jev") never receives a photo**: `src/lib/typesafe.ts` refuses any request that carries an image, and nothing calls it yet. Its key is env `TYPESAFE_API_KEY`.
- Only the 900 px copy of a photo is sent for naming, 8 photos per call plus neighbours for sequence context. The rules block is cached (measured: ~17.5k tokens, cache read works).
- Claim query: one `UPDATE … WHERE id IN (SELECT … FOR UPDATE SKIP LOCKED) RETURNING` so two tabs never name the same photo; a claim older than 6 minutes can be taken again; an answer is written only if the claim time still matches. Checked on a Neon dev branch `dev-photo-naming` (Postgres 18): 10 photos → 8, then 2, then 0; stale answer rejected. Production was not touched.
- Migration `0004_photo_desk.sql` is additive only (2 new tables, new columns, indexes). Its statements were applied to production on 2026-11-15 after the owner approved them, before the payment and admin migrations took numbers 0002 and 0003; the file was then renumbered and every statement made safe to run again (`IF NOT EXISTS`), so `npm run db:migrate` skips over what is already there.
- Uploads that were sent to storage but never registered are noted in `photo_uploads` and swept after 24 h on the next page load.
- Cost cap per case: env `PHOTO_COST_CAP_USD` (default 3). Measured on two real cases with 640 px photos: 42 photos ≈ 20 s and USD 0.09–0.13, 49 photos ≈ 22 s and USD 0.10–0.14. Real 900 px copies cost about twice that.
- Accuracy against the names the owner accepted on the old page (two cases, 91 photos): same name 67 %, right name among the 3 shown 82 %, 7 wrong names not flagged. This is weaker than the old trained model (the owner changed 1–3 names per case). Prompt tuning was stopped after three rounds to avoid fitting to two cases; the next step is a bigger set of accepted names or bringing the trained model in as a second opinion.
- Timings: one Claude call is cut at 120 s and tried at most twice, the naming route ends at 300 s, a claim can be taken again after 6 minutes. So a slice that is still running is never taken a second time.
- The claim time is compared as text with full microseconds (`claimed_at::text` out, `::timestamptz` in), never through a JS Date, so the guard on the result write matches (covered by the database test).
- The `jobs` table (created for stage 2, unused) is not used for photo naming: one job row per case cannot be split between two tabs, and each photo needs its own state for Retry and for naming by hand. The state lives on `case_photos` (`name_state`, `claimed_at`).
- Upload tokens: the path must sit under `<org>/<case>/photos/`, image types only, 25 MB, valid 10 minutes; a path that already belongs to a stored photo is refused.
- Cost cap: checked before each slice. Two tabs can each pass the check once, so the overshoot is at most one slice per open tab (about USD 0.02 to 0.05). USD 3 is the hard stop, USD 1 per 100 photos is the target.
- The case page does not link to this page yet (that page belongs to PR #7). Before it is linked: the owner decides on the measured accuracy (67 % same name), and a 25 MB full-size photo is opened once on a preview.
- Local runs without Blob: `PHOTO_STORE_DIR` (never in production).
- The page uses `AppLayout`, so it gets the white colour set (see "Two colour sets" below).

## Two colour sets (2026-11-15)
- Owner's rule: only the landing is dark ("Night Bay"); every app/workspace page is white. So the colour tokens in `tailwind.config.ts` are CSS variables with two sets in `globals.css`: the dark set on `:root` (landing, public site pages, 404) and a white set under `.theme-light`. `components/app-layout.tsx` (case list, new case, billing) and `components/auth-layout.tsx` (log in, sign up, password reset) wrap themselves in `.theme-light`; their route layouts export `lightViewport` from `lib/theme.ts`.
- A new signed-in page gets the white set by using `AppLayout`. Use the tokens (`bg-panel`, `text-fg`, `border-hair`, `bg-ice text-bay` for the primary action…), never a hex colour, so it follows the set it sits in.
- On white, the primary colour (`ice`) is ink black and the scan blue (`scan`) is the accent (progress, the lit top edge of a sheet). The logo's visor is filled in on white so its two white eyes stay visible.
- `public/landing/bay-*.jpg` were rendered again with `scripts/landing-posters.mjs`: they now show the white face ball, like the live 3D scene.

## Admin backoffice (plan: issue #4)
- Lives at `/admin` on app.autopilotclaim.com (not a separate host). A `backoffice.` alias can be added later as a Vercel domain plus a host rewrite.
- Access: verified email listed in env `ADMIN_EMAILS` (comma list; missing/empty/malformed = nobody) and a session younger than 12 h. Everyone else gets the same 404 as any missing page. No `/api/admin/*` routes exist; all reads happen in server components.
- Internal accounts (smoke account, `ADMIN_EMAILS`, `ADMIN_EXCLUDE_EMAILS`) are left out of every number unless `?internal=1`.
- Every Claude call goes through `trackedParse()` in `lib/claude.ts` and lands in `llm_calls` (one row per billed response, unique `request_id`; failures get `ok=false`). Prices live in `lib/pricing.ts` (`PRICES`); an unknown model is stored unpriced, never guessed. Update `PRICES` when `CLAUDE_MODEL` changes.
- `email_log` stores kind, recipient domain and outcome only.
- Org-wide spend comes from the Anthropic Admin API (`ANTHROPIC_ADMIN_KEY`), best-effort cached per instance. The response shape was written from the docs and is tested against mocks; confirm it against the first real response.
- Tests: `npm test` runs unit tests anywhere; the seeded database tests run only when `DATABASE_URL` points at a local Postgres with the migrations applied.

## Two hosts, one deployment (2026-11-15)
- The system is on the app host (env `BETTER_AUTH_URL`, `https://app.<domain>`); the bare domain and `www.` are the marketing site. Better Auth refuses a sign-in posted from the bare domain (wrong origin, 403) and a session made on one host does not exist on the other.
- So `src/middleware.ts` sends log in, sign up, password reset, the case pages, billing and admin asked for on the bare domain to the same path on the app host (`lib/hosts.ts`, tested), and the public top bar and the landing's Sign up button link straight to the app host there. Previews (`*.vercel.app`) and localhost are left alone. No new env variable.
- Case list (owner, 2026-11-15): one line per case. A case that stopped reads "On hold" and has no button (the team picks it up); the words "Try again" and "rejected" are not shown to users.
- Dates a signed-in page prints are formatted in `Asia/Kuala_Lumpur`, so the server and the browser write the same day.

## Merimen connection by browser extension, P1 (plan #38)
- App side only, off by default at three levels: env `EXT_CONNECT=on`, a per-org row in `ext_org_settings` with `enabled`, and a stored consent reference. With the env switch unset nothing touches the database, so production works before migration 0005 is applied.
- Deviation from the plan text: the per-org switch lives in its own table `ext_org_settings` instead of a column on `organizations`, so an unapplied migration can never break existing org queries.
- Not in P1: pairing-code exchange, install tokens, jobs, the extension, any Merimen action. Tables for them exist in migration 0005 so the owner approves one migration.
- Migration 0005 is additive and safe to run again. It is NOT applied in production; the owner approves it first.

## Linux worker (2026-11-21)
- Browserbase stays in the code and stays off unless `WORKER_UI` is unset. `WORKER_UI=on` shows the worker on `/connection` and on the case page instead of the live view.
- Saving a Merimen login uses the PR #39 gate (env `EXT_CONNECT=on`, `ext_org_settings.enabled` with a consent reference, and a row in `ext_consents`). The password is sealed with AES-256-GCM under `MERIMEN_CRED_KEY` and is not written to logs or returned to the browser.
- The worker tries that login once (`MERIMEN_LOGIN=on`). A wrong password, a lock (`locktime=15`), or a page it cannot read blocks the org: Merimen jobs pause, cases go to `waiting_user`, and the case log plus the banner (Chinese and English) ask for a new login. A later success queues the paused jobs again. There is no automatic second try.
- Migration `0007_worker.sql` is additive and is NOT applied in production.

## Linux worker: database over HTTPS and progress screenshots (2026-11-21)
- The worker box cannot reach Neon on port 5432. `DB_TRANSPORT=http` (default) uses Neon's SQL-over-HTTPS endpoint; `tcp` keeps psycopg. Job claim is one atomic `UPDATE … RETURNING` with a lease that the holder renews; a stale lease puts the job back.
- Progress screenshots are taken only with `WORKER_UI=on`, only from a logged-in claims page (never a page with a password box), and go to the private Blob store at `screenshots/{userId}/{caseId}/…`. Only the user who submitted the case can see them: other users in the same organisation and other organisations get 404 from the route. Retention `SCREENSHOT_RETENTION_DAYS` (default 90); the cleanup sets `deleted_at`, no SQL DELETE.
- Migration `0008_case_screenshots.sql` is additive and idempotent and is NOT applied in production. It numbers after this PR's own 0007.

## Hard test and QC round 1 (2026-11-21)
- Credits per case: 1,000 credits are taken when a case is created, only when `CREDITS_ENFORCE=on`. It is OFF by default, so production behaviour does not change until the owner sets it. `CREDITS_EXEMPT_ORGS` (comma-separated org ids) skips the charge for the owner's own orgs. A zero balance answers 402 before any file is uploaded. A failure on our side (not a bad file) refunds the case; a retry of a failed case takes 1,000 again only if it was refunded.
- Migration `0011_case_credit_once.sql` is one idempotent unique index (one case charge per case) and is NOT applied in production.
- Upload rules (types, 500 MB per file, 25 MB per PDF, 300 files, 2 GB total) live in one client-safe file shared by the form, the upload route and the case API.
- Zip bundles are unzipped on the server (limits: 300 entries, 250 MB total, ratio 200); photos in them go to the photo desk.
- Case events keep their English text in the database (the retry counter reads it) and are translated at render time.
- When `WORKER_UI` is on, the privacy and FAQ copy says the Merimen password is stored encrypted; when off, the old "we never store it" copy stays.
